# VirtualDJ config

VirtualDJ reads everything from `~/Library/Application Support/VirtualDJ/`.
Dotter symlinks two directories from this package into it:

| Repo path | Deployed to |
|---|---|
| `Mappers/` | `…/VirtualDJ/Mappers` |
| `Pads/` | `…/VirtualDJ/Pads` |

`Pads-Archive/` is source-only — kept for reference, not deployed.
`settings.preset` is data for `vdj-settings` (below), also not deployed.

## Why settings.xml is not tracked

It looks like the obvious thing to symlink. It isn't. `settings.xml` is closer to
a scratchpad than a config file:

- **It carries live credentials.** `internet/tidalAccessCode2` is a 520-char
  Tidal auth token; `internet/internetLogin` is the account email. This repo is
  public. (Beatport is *not* in here — VDJ keeps that session under
  `…/VirtualDJ/Cache/Beatport/<userid>/`, and the other service fields —
  Deezer, SoundCloud, gdrive/dropbox/onedrive/icloud — are empty.)
- **Most of it is machine state, not preference.** CoreAudio device indices
  (`coreaudio://134 (DDJ-GRV6)`, which renumber per boot), 17 window geometry
  records, `lastSelectedFolder`, `lastTrackListDate`. None of it transfers to
  another Mac.
- **VirtualDJ rewrites the whole file on quit.** Every session produces a diff,
  and a file-level symlink may not even survive that rewrite if VDJ replaces
  rather than edits in place.

So: track the settings worth keeping in `settings.preset`, and write them into
`settings.xml` on demand with `vdj-settings`. This never runs during a deploy.

## vdj-settings

Lives at [`config/zsh/bin/vdj-settings`](../zsh/bin/vdj-settings), deployed to
`~/.zsh/bin/`.

```bash
vdj-settings get automation/autoGain             # read one value
vdj-settings set controls/pitchRange=8.0         # write one
vdj-settings list quantize                       # find keys (substring match)
vdj-settings diff                                # preset vs. live settings.xml
vdj-settings apply                               # write the preset back
vdj-settings export                              # regenerate the preset
```

`set` takes any number of `key=value` pairs and reports each one as
`old -> new`, or `(unchanged)`.

### Keys

Keys are leaf tag names from `settings.xml`, optionally group-qualified:
`autoGain` and `automation/autoGain` are the same key. Qualify them in the
preset — 520 addressable settings is a lot of namespace, and the group tells you where it
lives in VDJ's own preferences UI.

An unknown key is an error, not a silent no-op, with close matches suggested:

```
$ vdj-settings get autogian
error: unknown setting: autogian. Did you mean: autoGain, autoPitchRange?
```

Not addressable: the repeating records inside `audioConfig` (audio device
routing), `skinWindows` (window geometry), and `controllers`. Those are
positional, per-machine, and not worth templating.

### Flags

Flags go **after** the subcommand — `vdj-settings set --dry-run k=v`, not
`vdj-settings --dry-run set k=v`. (Argparse lets a subparser default silently
clobber a value given before the subcommand, which could point `--file` at the
wrong settings.xml; defining them only on subcommands makes the wrong order
fail loudly instead.)

| Flag | Effect |
|---|---|
| `--dry-run` | print the plan, write nothing. Works while VDJ is running. |
| `--file PATH` | operate on a different settings.xml |
| `--force` | write even while VirtualDJ is running |

### Safety behaviour

- **Refuses to write while VirtualDJ is running** (`pgrep -x VirtualDJ`), because
  VDJ holds the file in memory and rewrites it on quit — your edits would vanish.
  `--force` overrides. Reads and `--dry-run` are never blocked.
- **Backs up** to `settings.xml.vdj-settings.bak`, overwriting the same file each
  run rather than accumulating timestamped copies.
- **Writes atomically** (temp file + `os.replace`) and **validates the result
  parses as XML** before swapping it in.
- **Preserves VDJ's formatting.** It edits the raw text with a targeted regex
  instead of re-serializing the tree, so the CRLF line endings and tab indents
  survive. A two-key write changes exactly two lines.
- Writes set `modified="yes"`, which is how VirtualDJ marks a setting as
  deliberately changed from its default.

## settings.preset

Generated by `vdj-settings export`, which takes every setting VDJ has flagged
`modified="yes"` — i.e. exactly what you've changed from stock — and filters out
what shouldn't travel:

- names matching `login|password|accesscode|token|secret|apikey`
- names starting with `last` or `autoUpdate` (session state)
- values containing `/Users/`, `/Volumes/`, or `com~apple~` (machine-specific paths)

Excluded keys are listed as comments at the bottom of the preset rather than
dropped silently, so you can see what was held back and why. Currently 223 kept,
6 excluded.

Hand-editing the preset is fine — it's `key = value`, `#` for comments, and
`export` is only needed when you want to recapture the live state wholesale.
Note that `export` overwrites the file, discarding hand edits and comments.

### On a new machine

```bash
setup/macos/deploy.sh     # Mappers + Pads
vdj-settings apply        # the 223 tracked settings
```

Two preset entries point at assets this repo does not track:
`skins/skin = DeathDisco Grave Raver v1/:skin` and `sampler/samplerBank = DRUMS`
(`Skins/` is 80 MB, `Sampler/` 453 MB). `apply` sets the values, but VDJ falls
back to defaults until those assets are in place.

## Related commands

| Command | Purpose |
|---|---|
| `vdj-purge-db` | strip all cues from `database.xml` (backs up first) |
| `vdj-link` | list linked tracks in the database |
| `virtualdj-sort-pad-pages` | sort `controls/padsPagesOrder` alphabetically — also edits settings.xml, predates this script |
| `virtualdj-post-process` | `database.xml` maintenance: stem flags, clear missing tracks |
| `vdjstems-*` | stem file tooling — see [docs/vdjstems-format.md](../../docs/vdjstems-format.md) |

Never track: `database.xml` (library data), `Cache/` (2.1 GB), `Skins/`,
`Plugins64/`, `PluginsMacArm/`, `license.dat`, `settings.xml`.
