The output you're on is one menu item

The guard synthesis kept every device as a three-line row and put the facts nowhere. This iteration borrows the wifi-widget's shape: the selected output becomes one larger graphite card with its format, I/O state, latency and identity in an inset underneath, and every other device shrinks to one compact line with its level and lock. The rules, the colours and the menu bar styles are unchanged. Pick a style, then go through the scenarios.

The selected output is one menu itemv2

The header used to be two disabled lines and then every device got the same three-line row, so the current output was only a blue tint. Now it is the same row as the devices below, grown into a card: glyph, name and bus pill, a meta line, the volume line, and an inset in three groups. Format: sample rate, bit depth, channels. State: rule, I/O, buffer, latency. Identity: data source, clock, UID. The current output is no longer repeated in the list.

Hover to copy. The UID row highlights on hover and copies on click, which is what you paste into a --dump comparison or a settings file.

Graphite card

Same reasoning as the wifi-widget: a blue block outweighed the whole menu. The card is a dark graphite panel and the state colour lives in the glyph and the header dot: green for the confirmed performance route, red when it is missing, amber for a caught fallback, plain white otherwise. Blue is left for the shield and the primary action.

Other outputs are one line eachv2

Glyph, name, bus, then on the right a five-segment mini level (dim when muted) or the word muted, and the lock. The three-line row with its own full-width bar is gone: you set a level on the device you're on, and the list is for routing. Click the line to route to it, click the lock to cycle its rule. Always Mute rows keep the dashed border; a missing Never Mute device stays listed in red with what to check.

Card anatomy

What the inset says, and where each line comes from

Everything on the card is a cheap HAL property read, all of them already fetched or one address away from what read_device collects today. Nothing is measured, tapped or listened to: the card describes the setting and the device's own reports, never the signal.

1

Big numbers: format

48 kHz is the nominal sample rate, 24-bit the physical stream format's bit depth (blank when the stream keeps it to itself, as HDMI often does), and 10 out · 12 in the stream-configuration channel counts. The old spec line, split into three glances.

2

Rule

Repeats the lock in words, with the count that matters: Never Mute · read-only for the shielded device, Always Mute · re-muted 3× this session for the padlock, showing the enforcement listener doing its job. No rule reads none, so the row's presence is the same in every scenario.

3

I/O

Running or Idle, from the device's is-running-somewhere flag. It answers the pre-gig question the old design could only guess at: is the DJ software actually holding the mixer. It says nothing about whether anything is audible, which the card is honest about.

4

Buffer and latency

The buffer frame size and its length at the nominal rate (512 fr · 10.7 ms), and the device's reported output latency plus safety offset. Both are the device's own numbers, not a round trip; they tell you what a change in Audio MIDI Setup or the DJ app did.

5

Source and clock

Source is the data-source name for devices that have one (the built-in output reports Internal Speakers or Headphones, which is the only way to tell the jack apart). Clock is the clock-source name where the device exposes one; a USB mixer usually doesn't, and the row is hidden rather than filled with a guess.

6

UID

The CoreAudio device UID, the key the rules are stored under. Monospaced, ellipsised, copy on click; the tooltip carries the whole string. This is the one line whose value you'd ever need to paste somewhere.

Edge states

Missing evidence stays visible

Fixed-level device

A DAC or USB mixer with no settable volume (volume: None) keeps its volume line, drawn as a hatched track with Fixed level · set on the device. The mute speaker stays if the device can mute; otherwise it dims and is disabled. The line never disappears, so the card's height does not jump between devices.

No output device

Menu bar: slashed speaker, no tag, no bar. Menu: the header reads No output device and the card is replaced by one disabled line. Ruled-but-disconnected devices still list below, since their absence is the information.

Aggregate or virtual device

An aggregate (Loopback, BlackHole, a Multi-Output) has no bus, so it wears an AGG or VIRT pill instead. Its format numbers are the aggregate's; the sub-devices are not listed, because the HAL's rule for which one is the master clock is not something the widget should restate.

Bluetooth codec

The HAL does not expose which codec AirPods negotiated, so the card does not claim one. The bit depth and rate it shows are what CoreAudio presents to apps, which is a real number and the honest one.

Build notes

What it reads, and from where

Already read

Format and volume

NominalSampleRate, StreamFormat on the first output stream for bits, StreamConfiguration for channels, VolumeScalar and Mute on the main element. All in audio.rs today; the card only lays them out differently.

One address each

State rows

kAudioDevicePropertyDeviceIsRunningSomewhere for I/O, BufferFrameSize, Latency and SafetyOffset on the output scope for the timing rows. Each is a get::<u32> through the existing helper, listened to with the same property-listener path so the card repaints when the DJ app opens the device.

Where the device has one

Source and clock names

DataSource then DataSourceNameForIDCFString, and the same pair for ClockSource. Both go through AudioObjectHasProperty first and the row is omitted when the device lacks it. Built-in output has a data source; most USB mixers have neither.

Already stored

Re-mute count

The enforcement listener already runs inside the HAL callback; it gains a per-UID counter for the session. It resets on launch and is never persisted, because the number is only interesting as "something keeps unmuting this".

Not on the card

Signal metering

No process tap, no level meter. The bar is the volume setting and the card's I/O row is the nearest honest thing to "is sound flowing". A meter would need an aggregate tap that touches the Never Mute device, which the rules forbid.

Worth a look

Route tag for long names

The menu bar tag is the first four letters of the device name, so AirPods Pro becomes AIRP and External Headphones becomes EXTE. The preview shows what the code does today. A per-transport fallback (BT, PHONES) would read better and is a small change in Device::tag.
